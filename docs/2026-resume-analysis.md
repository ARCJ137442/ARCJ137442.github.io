# 简历叙事分析（公开脱敏版）

> 本文仅保留可复用的写作方法，不包含个人简历原文、身份信息、联系方式、私人项目清单、未公开指标或日记摘录。

## 从“列出技能”转向“说明问题与贡献”

技术简历常见的两种组织方式是按编程语言列清单，或按项目说明做过什么。更便于读者判断的写法，是围绕问题、个人职责、决策过程和可验证结果展开。

| 写法 | 读者能看到什么 | 需要补充什么 |
|---|---|---|
| 技术清单 | 使用过哪些工具 | 熟练程度、实际场景和结果 |
| 项目列表 | 参与过什么项目 | 个人职责、协作边界和可核验成果 |
| 问题与贡献 | 为什么做、承担什么、改变了什么 | 公开链接、版本或其他证据 |

## 叙事可以怎样变化

一份早期简历可能主要写“希望参与团队”或“熟悉某些语言”；有了实践后，可以改为描述已经完成的贡献和责任。修改时不要把愿望写成业绩，也不要用代码行数、仓库数量或未经核对的指标替代影响。

个人兴趣也可以成为叙事线索，但应当服务于读者理解工作，而不是用私人日记、心理标签或生活经历填充简历。

## 一个可公开的项目条目

- **问题：** 目标用户或维护者遇到什么具体障碍？
- **职责：** 哪部分由自己负责，和团队/上游的边界是什么？
- **决定：** 做了哪些选择，为什么？
- **结果：** 哪些变化已由测试、发布记录或公开使用证据支持？
- **状态：** 已发布、试验中、维护中或归档？
- **来源：** 可公开访问的代码、Issue、Release 或演示链接。

如果项目处于私有状态，应使用概括性描述或完全省略，不公开仓库清单、客户信息、内部指标或未发布路线图。

## 发布前检查

1. 每项贡献都能由公开来源核验；不确定的数字改成定性描述或删除。
2. 删除姓名、私人邮箱、电话号码、家庭/学校地址、账号标识和个人文件路径。
3. 区分个人工作与团队成果，不把协作结果归为单人完成。
4. 删除私人项目、笔记、简历原文和反思内容；需要表达个人观点时另写经过本人确认的公开文章。
5. 检查 Markdown 当前版本和 Git 历史的公开范围。删除当前文件不会删除旧提交中的内容。

本文是通用写作指南，不是任何个人的简历或背景事实陈述。
